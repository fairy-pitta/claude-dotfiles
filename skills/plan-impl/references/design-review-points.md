# 設計段階で確認すべきレビュー観点

レビュースキル（backend-review / frontend-review）のチェックリストから、
**設計段階で気をつけておくべき観点** を抽出したもの。
コードを書く前に設計で潰せる問題を先回りで防ぐ。

---

## Backend: アーキテクチャ設計

| 観点 | 設計段階での確認方法 |
|------|-------------------|
| **Feature間直接依存の禁止** | 変更ファイル一覧で、Feature間の直接importが発生しないか。`shared/types/`経由にする設計か |
| **Domain層の純粋性** | Domain層（entities, repositories, enums）がDjango/DRFに依存しない設計か。`QuerySet`・`Model`等のインフラ概念が混入しないか |
| **Application層のORM非依存** | UseCase/Serviceが ORM Model を直接importせず、Domain Repositoryインターフェース経由の設計か |
| **DomainRepositoryがDTOを返さない** | Repositoryの戻り値がドメインモデル/VOであり、Presentation/Application DTOを返す設計になっていないか |
| **Transaction管理の配置** | `transaction.atomic()`がUseCase層でのみ管理される設計か。Repository層でのトランザクション禁止 |
| **1 class = 1 file** | 新規クラスが独自のファイルに配置される設計か |
| **既存パターンとの整合** | 既存のエラーハンドリングパターン、命名規約に従う設計か。独自実装を作っていないか |
| **既存の定数・型の再利用** | 既存の定数・型定義・Enumがあるのに、同等の値を再定義する設計になっていないか |

## Backend: データベース・パフォーマンス設計

| 観点 | 設計段階での確認方法 |
|------|-------------------|
| **N+1クエリの回避設計** | リスト取得で関連テーブルを参照する場合、`select_related()`/`prefetch_related()`の使用が計画されているか |
| **SELECT * 禁止** | `.only()`/`.values()`でカラムを絞る設計か |
| **インデックス設計** | フィルタ条件を変更・追加する場合、対象テーブルのインデックスが新しいクエリをカバーするか |
| **Bulk操作の検討** | 複数レコードの作成・更新で`bulk_create()`/`bulk_update()`を使用する設計か |
| **ページネーションの安定ソート** | `order_by`が明示され、同値タイブレーカー（PKなど）が含まれているか |

## Backend: 型安全・バリデーション設計

| 観点 | 設計段階での確認方法 |
|------|-------------------|
| **Result型の採用** | 戻り値にResult型パターンを使い、`result, error = usecase.execute()`の形式で受ける設計か |
| **Enum必須** | ステータス値・カテゴリ値に文字列リテラルではなくEnum（`TextChoices`/`IntegerChoices`）を使う設計か |
| **バリデーション実行順序** | 削除・更新の前にバリデーションが実行される設計か。副作用の後にチェックしない |
| **エンティティ不変条件** | ドメインエンティティの`__post_init__`で全フィールドのバリデーションが計画されているか |
| **UseCase層の引数ガード** | 引数間の依存関係がある場合、UseCase層でも防御的に検証する設計か |

## Backend: セキュリティ・認可設計

| 観点 | 設計段階での確認方法 |
|------|-------------------|
| **permission_classes明示設定** | 新規ViewにPermissionが明示的に設定される設計か。デフォルト依存禁止 |
| **認可バイパス経路の排除** | Result型の誤用やエラーハンドリング不備により認可チェックがスキップされる経路がないか |
| **スコープ付き権限の対象リソース検証** | 「操作者が権限を持つか」だけでなく「対象リソースがそのスコープに属するか」も検証する設計か |
| **冪等キーのスコープ** | cache keyにユーザーIDを含め、ユーザー間で衝突しない設計か |

## Backend: エラーメッセージ設計

| 観点 | 設計段階での確認方法 |
|------|-------------------|
| **エラーメッセージ定数化** | 新規エラーメッセージを `app/shared/constants/` で管理する計画か。文字列リテラル直書き禁止 |
| **ユーザー向け/内部向けの分離** | Msg/InternalMsg の分離を意識した設計か |

## Frontend: FSDアーキテクチャ設計

| 観点 | 設計段階での確認方法 |
|------|-------------------|
| **依存方向の遵守** | `app → pages → features → entities → shared`の方向のみ。逆方向の依存が設計に含まれていないか |
| **index.ts公開API経由** | 外部スライスの内部モジュールへの直接importが発生しない設計か |
| **features間直接import禁止** | features間で共有が必要な型・ロジックは`entities/`か`shared/`に昇格する設計か |
| **3+スライスからの参照は昇格** | 3スライス以上から参照されるコードを上位層に昇格する計画があるか |
| **UI配置の判定** | 業務操作→`features/*/ui/`、単一エンティティ表現→`entities/*/ui/`、画面専用→`pages/*/`、汎用→`shared/ui/` の規約に従っているか |
| **Vue SFCからの型エクスポート禁止** | 型は`model/types.ts`に定義し、`.vue`ファイルから`export type`しない設計か |
| **shared層にビジネスロジック禁止** | shared配置のコードが業務概念を知らない設計か |

## Frontend: 型安全設計

| 観点 | 設計段階での確認方法 |
|------|-------------------|
| **any型禁止** | `unknown`/`never`/ジェネリクス/型ガードで代替する設計か |
| **enum禁止** | `const + as const + typeof`で代替する設計か |
| **型アサーション原則禁止** | `as`キャスト・`!`(non-null assertion)を使わず、`?? デフォルト値`/型ガード等で代替する設計か |
| **toEntity()変換** | APIレスポンスのsnake_caseをそのまま使わず、`toEntity()`でcamelCaseドメイン型に変換する設計か |
| **型定義の配置** | ドメインモデル型→`entities/*/model/`、APIスキーマ→`entities/*/api/`、フォーム→`features/*/model/`、汎用→`shared/types/` |

## Frontend: 状態管理設計

| 観点 | 設計段階での確認方法 |
|------|-------------------|
| **状態の3分類** | サーバー状態→TanStack Query、クライアントグローバル状態→composable singleton、ローカルUI状態→コンポーネント内ref の分類に従っているか |
| **Pinia使用禁止** | Piniaの`defineStore`を使用しない設計か |
| **composable singletonのreadonly保護** | module-levelのrefを`readonly()`でラップして公開する設計か |
| **Props バケツリレー防止** | 3階層以上のprops受け渡しが発生しない設計か。provide/inject等で解決する計画か |
| **module-level singletonのリセット** | ページ遷移時にonUnmountedでクリーンアップする設計か |
| **認証境界でのキャッシュクリア** | メモリキャッシュをログアウト・セッション切れ時にクリアする設計か |

## Frontend: エラーハンドリング設計

| 観点 | 設計段階での確認方法 |
|------|-------------------|
| **console.* 禁止** | `shared/lib/logger.ts`経由で出力する設計か |
| **エラー4層パイプライン** | pages層で`normalizeAxiosError`を直接使わず、entities層に`mapBackendError`を配置する設計か |
| **Zodランタイムバリデーション** | 認証・権限・金額等のクリティカルなAPIにZod検証が計画されているか |

## テスト設計

| 観点 | 設計段階での確認方法 |
|------|-------------------|
| **テスト命名規約** | `test_<action>_<condition>_<expected_result>`の命名案が設計書に含まれているか |
| **正常系+異常系の網羅** | 正常系のみでなく、バリデーションエラー・権限不足・NotFound等の異常系テストも計画されているか |
| **境界値テスト** | エッジケース（0、空、None、上限値±1）のテストが計画されているか |
| **N+1クエリ検証** | 新規APIに`django_assert_num_queries`でクエリ数アサーションを追加する計画か |
| **認可テスト** | 権限不足・他社リソースアクセス等の拒否テストが計画されているか |
| **副作用否定テスト** | 失敗時に副作用（save, delete等）が実行されないことを検証するテストが計画されているか |
