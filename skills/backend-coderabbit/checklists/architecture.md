# Backend Review: Architecture + Code Organization + Syntax

このチェックリストはサブエージェント用。`backend/` 配下の変更ファイルに対して適用する。

**コード例示:** `references/code-examples.md` を参照

---

## Core Checklist

### Architecture

- [ ] **レイヤー依存方向の遵守** — 依存方向「Application → Domain ← Infrastructure」に従っているか。Domain層（entities, repositories, enums）がDjango/DRF/インフラ概念（`QuerySet`・`Model`等）に依存していないか、Application層のサービス・ユースケースがORM Model（`from app.models import ...`）を直接importしていないか確認する。ORM操作はInfrastructure層のRepository実装に配置し、Application層はDomainインターフェースのみに依存させる
- [ ] **Feature間直接依存** — 通常Feature間の直接import（例: journal→accounting）がないか。`shared/types/`経由が必要。全Feature→shared/・user/・organization/ は許可
- [ ] **DomainRepositoryのDTO依存・実装詳細漏洩** — Domain層のRepositoryが`AuthUserPayload`等のPresentation/Application DTOを返していないか。ドメインモデル/VOを返しUseCase側でDTO変換すること。また抽象メソッドのdocstringに「UPDATE ... WHERE」等のSQL/ORM実装詳細が含まれていないか確認する。振る舞いはドメイン用語で記述し、実装方法はInfra層に委ねる（→ `references/code-examples.md`）
- [ ] **Transaction管理の配置** — `transaction.atomic()`がUseCase層でのみ管理されているか。Repository層でのトランザクション禁止
- [ ] **transaction.atomicとロールバック漏れ** — atomicブロック内で部分コミットを招くロールバック漏れがないか確認する。例: Result型パターンでは例外を投げないためエラーチェックをatomicブロック内に置きエラー時にRuntimeErrorをraiseする。複数書き込みでは後続失敗時に備え全`return failure()`前に`set_rollback(True)`を追加する。漏れるとトークン無効化だけコミットされる等の部分コミットバグになる
- [ ] **トランザクション外副作用の並行リスク** — トランザクション外でメール送信等の副作用を実行する場合、その間に他リクエストが状態を変更し送信内容が無効になる競合がないか検証する。特にcooldown=0等の設定で競合窓が広がるケースに注意
- [ ] **Viewでバリデーション直書き禁止** — View層でバリデーションロジックを直接実装していないか。バリデーションはSerializer/UseCase層に配置し、View層は入力の受け取りとレスポンス変換のみ
- [ ] **既存パターン・定義の無視と独自実装** — 既存のエラーハンドリングパターン（共通エラーハンドラ・例外変換等）・定数・型定義・Enumがあるのに無視して独自実装/再定義していないか。既存定義を検索して再利用し、既存パターンに沿わない不要なファイル増殖を防ぐ
- [ ] **バックエンド/フロントエンド間のスキーマ不一致** — APIレスポンスのフィールド名・型・構造がフロントエンドの期待するスキーマと一致しているか確認する。スキーマ不一致はサイレントなバグの原因になる
- [ ] **不要な条件分岐（フレームワーク自動処理）** — フレームワーク（Django/DRF）が自動的に処理する部分に不要な条件分岐を追加していないか。例: DRFが自動的にNone/空文字を処理するフィールドへの手動チェック
- [ ] **コードの意図明確性** — 暗黙的な振る舞いに依存せず意図が明確に読み取れるか。Optionalにして明示的にチェックする、命名で意図を伝える等
- [ ] **1 class = 1 file** — 各クラスが独自のファイルに配置されているか

### Syntax & Basic Quality

- [ ] **構文エラー** — importの括弧閉じ忘れ、未解決のマージコンフリクトマーカー（`<<<<<<<`）
- [ ] **命名規約** — CLAUDE.md準拠（`{action}_{entity}_usecase.py`, `{Entity}RepositoryImpl`等）
- [ ] **未使用コード** — 未使用の関数・import・型定義・定数・パラメータがないか。関数シグネチャに存在するがボディで未使用のパラメータはAPI契約の誤解を招く
- [ ] **会話文脈・実装履歴コメントの削除** — 次のコメントは削除を指摘する。①AIエージェントとの会話内でしか得られない文脈（「指摘により修正」「リクエスト通り」等）、②以前の実装との比較・変更経緯（「旧実装ではforループ」「N+1を解消」等）、③コード単体を読んでも意図が伝わらない（PR/diff/会話に依存する）コメント。コメントは将来の読者に「なぜこうあるか」を説明するものに限る（意図を説明する有用なコメントは保持し、誤って削除指摘しないこと）
- [ ] **コメント正確性** — コメントが実際のコードの挙動と一致しているか
- [ ] **ドキュメント内ファイルパス参照の正確性** — リファレンスドキュメント内のファイルパスが実際のファイル名と一致しているか確認する。特にファイル名の単数/複数形の不一致に注意

## Extended Checklist

### Architecture（詳細）

- **Presentation→Infrastructure直接依存** — ViewやSerializerがRepositoryImplを直接参照していないか。UseCase経由が必要
- **フィルタ除外と永続化の不一致** — 「フィルタ除外」と「状態遷移の永続化」が一致しているか。exclude_expired_pendingのようなフィルタは表示上の除外でありデータの整合性を保証しない。一覧系APIで期限切れを永続化する設計判断が必要
- **終端状態の関連エンティティ削除後の一覧取得耐性** — 終端状態（APPROVED等）の申請が参照する関連エンティティ（会社・ユーザー）が削除される可能性を考慮しているか。特に削除ジョブが存在するフローでは、一覧取得時に欠損を許容する設計が必要
- **論理削除エンドポイントのREST規約準拠** — 論理削除を実装する際、DELETE メソッドを使用しREST規約に準拠しているか。POST /deactivate/ のようなアクションベースURLではなく DELETE /resources/{id}/ が標準的
- **ロールスコープ階層の冗長grant防止** — ロールのスコープ階層（GLOBAL > REGION > COMPANY）を意識し、上位スコープのロール保持時に下位スコープのgrant作成が不要かを確認する。複数ロール併有ケースでは上位スコープが下位を包含するため、冗長なgrantは作成しない

### Code Organization & DRY（詳細）

- **DRY原則違反** — 同一・類似のヘルパーメソッドやバリデーションロジック・QuerySetフィルタが複数箇所に重複していないか。複数UseCaseに同じロジックがある場合や3箇所以上の完全重複（例: `exclude_expired_pending`が`search`/`count`/`search_approvable_requests`に重複）はhelper化して条件のズレを防ぐ。`save()`と`find_*()`で同じ`Entity.reconstruct(...)`が重複する場合は`_to_entity(obj)`に抽出
- **入力型だけ異なる同一アルゴリズムの重複** — 入力型が異なるだけでロジックが同一の関数ペアがないか。型変換部分を分離して共通化すべき。2箇所でもメンテリスクがある
- **メソッド間の同一集計再計算** — メインメソッドで作成した集計結果(dict等)をサブメソッドに渡さず再計算していないか。O(n)走査の不要な繰り返しを防ぐ
- **事前構築データの一貫使用** — `prepare()`等で構築したデータを後続処理に渡さず元の入力を再利用していないか。保存用データとストリーム用データの出所が同一であることを確認する。「事前構築 → 使用」の流れで構築結果が一貫して使われていないと二重化バグや不整合の原因になる
- **不要な中間ファイル・ラッパー** — 薄いラッパーやパススルーだけの中間ファイルが作られていないか。直接呼び出しで十分な場合は中間層を省く
- **dict comprehensionの重複キー上書きバグ** — `{key: value for ...}`は同一キーで後の値が上書きされる。集計が必要な場合は加算ループに変更（→ `references/code-examples.md`）
- **サイレントドロップより明示的エラー返却** — list comprehension内のNoneフィルタでデータを捨てるのは危険。存在すべきデータが欠損している場合は`failure(ValueError(...))`を返す（→ `references/code-examples.md`）
- **Moduleレベルシングルトンとインスタンス変数の重複** — ステートレスなCalculator/Serviceの初期化方法を統一する
- **到達不能コードの検出** — 防御ガード（`if not x: return`）が上流のバリデーションで到達不能になっていないかチェック。冗長な防御コードはテストカバレッジを下げ保守コストを増やす
- **Deprecated API使用** — 非推奨のDjango API（例: `CheckConstraint`のclass引数）を使用していないか
- **設定値マジックナンバーの定数化** — TTL・タイムアウト等のビジネス設定値がローカル変数にハードコードされていないかチェック。constants/に定義して一元管理する
- **設定変数の上書き検出** — settings.pyで条件分岐により変数をインポートした後、同じ変数を無条件に再定義していないかチェック。Pythonでは後続の代入が前の代入を上書きするため、条件付きインポート＋無条件ハードコード定義の組み合わせは常にバグとなる。条件付きインポートが存在する場合、後続の定義も対応するelse/notガードで囲むこと
- **for_updateメソッドのdocstring** — `select_for_update()`を使用するリポジトリメソッドのdocstringにトランザクション内で呼び出す必要がある旨を明記しているか。欠落すると呼び出し側がトランザクション外で使用するリスクがある
- **カーソルページネーションのソート契約明記** — cursorを受け付けるrepository interfaceに、結果がどの順序（`-requested_at, -id`等）で返るかがdocstringで明記されているか。実装だけにorder_byがあってもProtocol契約が曖昧だと差し替え時に崩れる
- **型アノテーションスタイルの一貫性** — `Union[A, B]`と`A | B`が混在していないか
- **Django management commandの失敗伝播** — `handle()`メソッドがエラーケースで正常returnしていないか確認。Djangoではhandle()から例外が伝播しないとexit status 0になり、CI/CDがエラーを検出できない。失敗時は`CommandError`をraiseすること
- **ドキュメントと実装の同期** — 権限コードを追加・分離・削除・リネームした際、同一ドキュメント内の全セクション（一覧・マッピング・サマリー）を横断的に更新しているか。エンドポイント表のみ修正し下部セクションを失念しやすいため、変更時に旧権限名・旧個数をテキスト検索する
- **ドキュメントの可読性（凡例・主語）** — ドキュメントの凡例・記号説明がコンテキストなしで読む人にも伝わるか、テーブルセル内の説明文で主語を省略していないかを確認する。略称・記号は初出で定義を明示し、差分説明（「Xから〜を除外」等）はセル単体で意味が通る文にする
