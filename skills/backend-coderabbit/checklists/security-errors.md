# Backend Review: Security & Authorization + Error Messages & Constants

このチェックリストはサブエージェント用。`backend/` 配下の変更ファイルに対して適用する。

**コード例示:** `references/code-examples.md` を参照

---

## Core Checklist

### Security & Authorization

- [ ] **permission_classes明示設定** — DRF ViewにPermissionが必ず明示されているか。デフォルト依存禁止（→ `references/code-examples.md`）
- [ ] **認可バイパス経路** — Result型の誤用やエラーハンドリング不備により認可チェックがスキップされる経路がないか
- [ ] **認可ロジックの層自己完結** — 認可を担う層（UseCase/サービス/ドメイン）が、Presentation層（例: DRF `permission_classes`）に依存せず、直接呼び出し経路（他UseCase・バッチ・management command 等）でも権限を検証しているか。認可をView層だけに置くと内部経路でバイパスされる
- [ ] **オブジェクトレベル認可（IDOR/BOLA）** — リソースID（path/body の pk/uuid 等）を受け取るエンドポイントで、ログイン済み確認だけでなく「呼び出し元がそのリソースを操作してよいか」を検証しているか（認証≠認可）。IDを推測・列挙されると他テナント/他ユーザーのデータを参照・更新できる。取得クエリをアクセス可能範囲でスコープする（例: `filter(<所属>=request.user.<所属>, ...)`）か、取得後に所有権を検証し不一致は404/403を返すこと。`permission_classes` が `IsAuthenticated`/`AllowAny` のみで object-level 認可が無いViewは要注意
- [ ] **関数レベル認可の粒度（BFLA）** — エンドポイントごとに必要なロール/権限が操作の重要度に応じて設定されているか（例: `@require_permission`）。認可が宣言されていても、管理者専用操作（削除・権限付与・他者データ更新等）に下位ロールが到達できる粒度になっていないか確認する
- [ ] **スコープ付き権限の対象リソース検証** — REGION/COMPANYスコープの権限チェックで「操作者が権限を持つか」だけでなく「対象リソースがそのスコープに属するか」も検証しているか確認する。操作者の権限チェックのみだと、スコープ外のリソースを操作できる権限過大が発生する
- [ ] **作成・割り当て時の指定先認可（権限昇格防止）** — リクエストが操作対象の所属先・所有者・付与ロール（例: テナント/組織ID, owner, role）を指定する作成/割り当て/付与系で、呼び出し元がその指定先への権限を持つか検証しているか。汎用的な操作権限の保有だけで任意の所属先・ロールを指定できると、担当外スコープへの作成や権限昇格になる。一括（bulk）処理では各要素に同じ認可を適用すること
- [ ] **マスアサインメント防止** — 入力を一括でモデルへ書き込む際（例: DRF シリアライザの `fields = "__all__"` や広い `exclude`）、サーバ管理フィールド（owner/status/role/is_staff 等）まで書き込み可能になっていないか。書き込み可能フィールドは明示列挙し、サーバ制御フィールドは読み取り専用にすること
- [ ] **冪等キーのTOCTOU/スコープ** — cache.get/setの分離パターンは並行リクエストで競合するため、冪等制御にはcache.add()等の原子的操作を使い、エラーパスでのロック解放漏れがないか確認する。併せて認証必須APIのcache keyにユーザーIDが含まれているか確認する（ユーザーIDなしだと異なるユーザー間で冪等キーが衝突し正当なリクエストが拒否される）
- [ ] **機密情報・PIIのレスポンス/ログ露出** — パスワード・トークン・APIキー・個人識別情報（メール/氏名/電話等）がレスポンス（シリアライザのフィールド）やログ・例外メッセージに混入していないか。`str(e)` のユーザー露出だけでなく、ログ引数にもPIIを含めないこと
- [ ] **write_only on sensitive fields** — パスワード等の機密フィールドに`write_only=True`が設定されているか
- [ ] **秘密値のハッシュ保存・非返却** — 招待・パスワードリセット・メール認証等の秘密トークンをDBに平文保存していないか。ハッシュ化して保存し検証はハッシュ比較で行う（平文保存はDBダンプ・ログ経由の漏えい面を広げる）。併せて、秘密値をAPIレスポンス・シリアライザに含めていないか確認する
- [ ] **入力由来のSQL/コマンドインジェクション** — 外部入力を生SQL（例: `.raw()`/`.extra()`/`RawSQL`/`cursor.execute()`）やシェル実行に文字列連結・f-string で埋め込んでいないか。必ずパラメータ化（プレースホルダ）するか、ORM/安全なAPIで代替すること
- [ ] **APIレスポンスキー名の統一** — 手動構築のエラーレスポンス（`_validation_error_response`等）とApiResponse共通メソッドでキー名（camelCase/snake_case）が統一されているか確認する。不統一だとフロントエンドのエラーコード判定が分岐漏れしやすくなる

### Error Messages & Constants

- [ ] **エラーメッセージ定数化** — 文字列リテラルでエラーメッセージを直接記述していないか。`app/shared/constants/`（`PermissionErrors` 等）で管理し、新規追加時はリテラルでなく定数を参照する。ユーザー向けだけでなく開発者向けエラー（例: RuntimeError・Repository契約違反等の内部エラー）も対象（→ `references/code-examples.md`）
- [ ] **同一内部契約違反の定数再利用** — 複数usecaseで同じ契約違反（`Result` が error なしで `None`、Repository が `None` を返す等）を扱う場合、メッセージを raw 文字列で複製せず既存の共通定数を再利用しているか確認する。文言の分岐を防ぎテスト保守性を上げる
- [ ] **DRFフィールド制約のエラーメッセージ定数化** — DRFフィールドにmax_length/min_length/min_value/max_value等の制約を追加する際、error_messagesもセットでMsg定数化されているか確認する。DRFビルトインメッセージはプロジェクトの「エラーメッセージ定数化」ルールの対象外と見落としやすい。error_messagesパラメータで明示的に定数を指定すること。`allow_null=False`（デフォルト）のフィールドでは`null`キーの漏れにも注意（例: `IntegerField` で `required`/`invalid`/`min_value` を定数化しても `null` キーが漏れるとDRFデフォルト文言にフォールバックする）
- [ ] **ユーザー向け/内部向けメッセージの混在チェック** — Msg/InternalMsgの分離が不十分だとAPIレスポンスに内部メッセージが露出するリスクがある。メッセージ定数を追加する際、用途（ユーザー向け/内部向け）を確認して適切なクラスに配置すること
- [ ] **定数ファイルの責務分離** — メッセージ定数ファイルに設定値（TTL, 閾値等）を混在させていないか確認する。文言定数と運用設定値は別ファイルに分離すること。混在すると責務が曖昧になり保守性が低下する
- [ ] **except Exceptionで例外情報の保持** — `except Exception:` でcatchしてResult failureに変換する際、`except Exception as e` として `str(e)` を `ValidationError` の `details` に含めているか確認する。例外情報を握りつぶすとデバッグ困難になる
- [ ] **`logger`/`print`禁止** — `logger`・`print`（マイグレーションbackward含む）の使用禁止

## Extended Checklist

### Security（詳細）

- **デフォルト拒否原則** — `dict.get()` は「キー不在」と「値がNone」を区別できない。認可コードでは `key in dict` で明示的にチェックし、不在はデフォルト拒否とすべき。dict.get() を認可ロジックで使用していないか確認する
- **トークン無効化** — パスワード変更・ログアウト時にトークンが適切に無効化されているか
- **ファイルアップロード検証** — アップロードを受け付けるエンドポイントで、ファイルサイズ上限・MIMEタイプ/拡張子のallowlist・保存ファイル名のサニタイズ（パストラバーサル防止）を実装しているか確認する。`Content-Type` ヘッダのみを信頼せず実体も検証すること
- **SSRF（外部フェッチの宛先検証）** — 外部入力のURL（Webhook・画像取得・プロキシ等）をサーバ側から fetch する場合、スキーム/ホストのallowlist・内部IP/クラウドメタデータエンドポイント（`169.254.169.254` 等）への到達禁止・リダイレクト追従の制限を行っているか確認する
- **レート制限/throttle の適用範囲** — 総当たり可能な認証系（ログイン・パスワードリセット・OTP検証）に加え、高コストなエンドポイント（ファイルアップロード・一括処理・重い集計等）にもレート制限を設定しているか。未設定だと認証済みアカウントからの並列大量リクエストでリソース枯渇（DoS）を招く。認証系は試行回数ベースのロックアウトも併用する
- **入力サイズに比例したメモリ展開（DoS）** — アップロードファイルや大量レコードを全件一括でメモリ展開していないか（例: `file.read()` 全体読み込み・`list(csv_reader)`・QuerySet の list 化）。入力サイズに比例してメモリが急増する。ストリーミング/逐次処理（例: `iterator(chunk_size=...)`）に変更し、サイズ上限と併せて防御すること
- **依存ライブラリの脆弱性** — 追加・更新したパッケージに既知の脆弱性（CVE）がないか確認する。未メンテ・既知脆弱性のあるライブラリの新規導入を避ける
- **str(e) のエラー契約混入** — except ブロックで `str(e)` をユーザー向けレスポンスや Result の details に含めていないか確認する。内部例外テキストは不安定（ライブラリ更新で変わる）であり、テストも壊れやすくなる。デバッグ情報が必要なら structured logging に出力し、API 契約には定数メッセージのみ含める
