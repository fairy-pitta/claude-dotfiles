# Triage Issue

GitHub Issue の内容がコードベースに現存する問題かを検証し、該当する場合は dev ブランチからブランチを切って調査・計画・実装を行う。

Issue URL: $ARGUMENTS

**開始時アナウンス:** "triage-issue を開始します。Issue取得 → 現存確認 → ブランチ作成 → 調査・計画 → 実装 の流れで進めます。"

---

## Phase 1: Issue の取得と解析

### 1-1. Issue 情報の取得

```bash
# URL からリポジトリとIssue番号を抽出して取得
gh issue view "$ARGUMENTS" --json title,body,labels,state,comments
```

### 1-2. Issue の要約

取得した Issue から以下を抽出する:

- **問題の概要**: 何が起きているか
- **再現条件**: どういう状況で発生するか
- **期待される動作**: 本来どうあるべきか
- **関連キーワード**: コード検索に使えるクラス名・関数名・エラーメッセージ等

---

## Phase 2: コードベースでの現存確認

### 2-1. 調査（Explore エージェント）

Agent tool で Explore エージェントを **thorough** レベルで起動:

```
subagent_type: "Explore"
description: "issue existence check"
prompt: |
  以下の GitHub Issue がコードベースに現存する問題かどうかを調査してください。

  ## Issue
  タイトル: <Issue タイトル>
  内容: <Issue 本文の要約>

  ## 調査観点
  1. Issue で言及されているファイル・クラス・関数がコードベースに存在するか
  2. 問題のコードパターンが現在も残っているか
  3. 既に修正済み（関連するコミットやPRがある）ではないか
  4. 関連するテストが存在し、問題をカバーしているか

  ## 出力形式
  - **現存判定**: YES / NO / PARTIAL（一部修正済み）
  - **根拠**: 判定の根拠となるファイルパスとコード箇所
  - **関連ファイル**: 修正が必要になりそうなファイル一覧
  - **既存テスト**: 関連するテストファイルがあれば記載
```

### 2-2. 判定

Explore エージェントの結果に基づき判定:

- **NO（修正済み）**: Issue にコメントで報告して **スキル終了**
  ```bash
  gh issue comment "$ARGUMENTS" --body "調査の結果、この問題は既に修正済みであることを確認しました。クローズを検討してください。"
  ```
- **YES / PARTIAL（現存）**: Phase 3 へ進む

---

## Phase 3: ブランチ作成

### 3-1. ブランチ名の決定

Issue のタイトルとラベルからブランチ名を決定する:

- バグ修正: `fix/<簡潔な説明>`
- 機能追加: `feature/<簡潔な説明>`
- リファクタ: `refactor/<簡潔な説明>`

ブランチ名は英語・ケバブケースで、50文字以内。

### 3-2. dev ブランチから分岐

```bash
git fetch origin
git checkout -b <branch-name> origin/dev
```

**注意**: `origin/dev` が存在しない場合は `origin/develop` → `origin/main` の順にフォールバックする。

---

## Phase 4: 詳細調査と計画

### 4-1. 詳細調査（Explore エージェント）

Phase 2 の調査結果をもとに、より深い調査を行う:

```
subagent_type: "Explore"
description: "deep investigation for fix plan"
prompt: |
  以下の Issue を修正するための詳細調査を行ってください。

  ## Issue
  <Issue の要約>

  ## Phase 2 で判明した関連ファイル
  <関連ファイル一覧>

  ## 調査観点
  1. 問題の根本原因（root cause）の特定
  2. 影響範囲の特定（この問題が他のどの機能に波及するか）
  3. 修正に必要な変更箇所の洗い出し（ファイルパス + 行番号）
  4. 既存のテストで影響を受けるもの
  5. 類似の実装パターンがあれば参考として記載

  簡潔にまとめること。コード例は不要、パスと概要のみ。
```

### 4-2. 計画作成（Plan Mode）

Plan Mode に入り、調査結果をもとに実装計画を作成する。

プランに含める項目:

- **Issue**: Issue URL とタイトル
- **Root Cause**: 根本原因の説明
- **Goal**: 何を修正するか
- **Scope**: 変更対象のファイル一覧（絶対パス付き）
- **Phases**: 順序付きの実装ステップ（各ステップに具体的な変更方針を記載）
- **Testing Strategy**: 追加/変更するテスト（テスト関数名の命名案も含む）
- **Verification**: 各ステップの検証方法
- **Risks**: 破壊的変更、マイグレーション、パフォーマンスのリスク

### 4-3. プランをファイルに保存

`.claude/plan.md` に保存する。

### 4-4. ユーザー承認

計画を提示し、ユーザーの承認を待つ:

```
=== 実装計画 ===

Issue: <タイトル> (<URL>)
Branch: <branch-name>
Base: dev

## Root Cause
<根本原因の要約>

## 計画サマリー
<plan.md のフェーズ一覧を簡潔に>

このまま実装に進みますか？（修正要望があれば指示してください）
```

- **OK / 承認 / LGTM / 無返答で進行指示**: Phase 5 へ
- **修正要望あり**: プランを修正 → 再提示
- **却下**: `.claude/plan.md` を削除してスキル終了

---

## Phase 5: 実装（サブエージェントに委譲）

**実装はサブエージェントに委譲する。** メインコンテキストの消費を抑えつつ、plan.md に忠実な実装を行わせる。

### 5-1. Plan Mode を終了

Plan Mode を抜けて実装フェーズに入る。

### 5-2. 実装エージェントの起動

Agent tool で general-purpose エージェントを起動し、実装を委譲する:

```
description: "implement fix per plan"
prompt: |
  あなたは実装担当のサブエージェントです。
  `.claude/plan.md` に記載された実装計画に従って、コードを変更してください。

  ## ルール
  1. まず `.claude/plan.md` を Read tool で読む
  2. プロジェクトの CLAUDE.md を読む（規約確認用）
  3. Phases を上から順に実装する
  4. 各ステップで対象ファイルを Read → Edit/Write で変更
  5. Testing Strategy に従いテストを追加する
  6. 全変更完了後、プロジェクトのテストを実行して通過を確認する
     - テスト失敗時は修正して再実行（最大3回）
     - 3回失敗したら、失敗内容を報告して終了
  7. プランにない変更は一切行わない
  8. プランの順序を守る

  ## 出力形式
  - 変更したファイル一覧
  - 追加したテスト一覧
  - テスト実行結果（pass/fail + 詳細）
  - 問題があれば報告
```

### 5-3. 実装結果の確認

エージェントの返却結果を確認:

- **テスト全通過**: Phase 6 へ
- **テスト失敗あり**: 失敗内容をユーザーに報告し、判断を仰ぐ

#### Context check -> `/compact` if >= 80%

---

## Phase 6: コミット & 報告

### 6-1. コミット

`/commit-push` を使ってコミット＆プッシュする。

コミットメッセージルール:
- 変更内容が具体的にわかるメッセージにする
- 複数テーマにまたがる場合はコミットを分割する

### 6-2. 完了報告

```
=== Triage Issue: Complete ===

Issue: <タイトル> (<URL>)
Branch: <branch-name>
Base: dev

## 変更サマリー
<変更内容の概要>

## テスト結果
<テスト実行結果>

## Next Steps
- `/create-pr` で PR を作成できます
- `/self-review` でセルフレビューを実行できます
```

### 6-3. クリーンアップ

```bash
rm -f .claude/plan.md
```

---

## Critical Constraints

- **Phase 2 で現存確認するまでブランチを作らない** — 修正済みならブランチ不要
- **Phase 4 のユーザー承認なしで実装に入らない**
- **dev ブランチの存在確認を必ず行う** — フォールバック順序を守る
- **テスト通過を確認してからコミットする**
- **コンテキスト管理: 各フェーズ境界で 80% チェック → `/compact`**

---

## Red Flags - Never Do This

- **Issue を読まずに調査を始めない**
- **現存確認をスキップしてブランチを作らない**
- **main ブランチから直接ブランチを切らない**（dev 優先）
- **調査結果なしで計画を作らない**
- **ユーザー承認なしで実装を始めない**
- **テスト未実行でコミットしない**
