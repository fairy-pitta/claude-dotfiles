# Commit and Push Changes

Commit and push the current changes with strategic git practices.

Context: $ARGUMENTS

## 手順

### ステップ1: 現状把握

以下のコマンドを**並列**で実行:

- `git status`（未追跡ファイル確認。`-uall`は使わない）
- `git diff --staged`（ステージ済みの変更内容）
- `git diff`（未ステージの変更内容）
- `git log --oneline -5`（直近のコミットメッセージのprefixスタイル参照用）
- `git branch --show-current`（現在のブランチ名）

### ステップ2: ブランチ判定

- **main/master/devブランチの場合**: 絶対にコミットしない。ブランチ作成を促す
- **それ以外のブランチの場合**: そのまま続行

### ステップ3: テスト実行（必須）

コミット前に必ずテストを実行して通過を確認する:

- unit / integration テストが存在する場合は実行
- いずれかが失敗している場合はコミットせず、先に修正する
- テストが存在しない場合はスキップ

### ステップ4: ステージング判定

ステージ済みファイルがない場合:
- 会話の文脈や実装状況から、ステージすべきファイルを判断する
- `.env`、認証情報等のファイルが含まれる場合は警告する
- `git add -A` は使わず、個別にステージする

ステージ済みファイルがある場合はそのまま続行。

### ステップ5: コミットメッセージ生成

変更理由が不明な場合はユーザーに質問する。

#### 基本原則: 「なぜ」を記載する

変更内容（what）は `git diff` で確認できるが、変更理由（why）はコミットメッセージにしか記録できない。diffから読み取れる情報の優先度は低い。**会話の文脈**から以下を読み取りメッセージの主軸にする:

- **何が問題だったのか**（背景・課題）
- **このコミットでどう改善されるのか**（効果・目的）

typo修正などの自明な変更を除き、**必ず変更が必要だった理由を記載する。**

#### 主観的な判断には客観的根拠を添える

「不要」「不適切」「古い」「冗長」などの主観的な判断を含むコミットメッセージは、将来の開発者がその妥当性を検証できない。**なぜそう判断したのか**の根拠を必ず記載する。

❌ 悪い例:
```
不要なコードを削除
```

✅ 良い例:
```
未使用のUserSerializer classを削除

grepで検索した結果、プロジェクト内に呼び出し元が存在しない。
2024年のAPI v2移行時に旧エンドポイントと共に不要になったもの。
```

根拠として有効な情報の例:
- **検索結果**: 「grepで呼び出し元がない」「参照箇所が0件」
- **意思決定の経緯**: 「MTGで使用しないことが決まった」「issueで廃止が合意された」
- **技術的事実**: 「この機能はv2で別の実装に置き換えられた」「このライブラリはEOLを迎えた」
- **エラーや不具合の証拠**: 「本番でこのエラーが発生している」「CIでこのテストが失敗する」
- **数値データ**: 「レスポンスタイムが200ms→50msに改善」「メモリ使用量が16MB削減」

#### コミットメッセージの構造

```
1行目: type: 変更内容の簡潔な要約（50文字以内推奨）
2行目: 空行
3行目以降: 変更理由の詳細説明（問題の説明 → 解決方法の順、72文字程度で改行）
```

- **1行目**: 50文字以内を推奨（最大72文字）、命令形（「〜を追加」「〜を修正」「〜を削除」）、末尾に句読点は不要
- **3行目以降**: 変更理由を詳しく説明（自明な変更を除き必須）。具体的な数値やデータ、関連するissue/PR番号があれば含める

#### 本文が省略できる場合

変更内容が1行のサマリーで完全に理解でき、「なぜ」が自明な場合のみ省略可:
- typo修正
- lint/フォーマット修正

「不要コード削除」は本文省略不可。なぜ不要と判断したかの根拠が必要。

#### type選択フローチャート

```
ユーザーから見て新しい機能・振る舞いが追加される？
  → Yes → feat
  → No  → ユーザーが困っている不具合を修正した？
            → Yes → fix
            → No  → chore（より具体的な型があればそちらを使う）
```

その他の型: `refactor` / `perf` / `style` / `test` / `docs` / `ci` / `build`

破壊的変更がある場合は型の後に `!` を付ける（例: `feat!: APIレスポンスの形式を変更`）

#### 禁止表現（絶対に使わない）

以下のような**何をしたかが伝わらない抽象的なメッセージは禁止**:

| ❌ 禁止 | 理由 |
|---|---|
| `fix: PRレビュー指摘を反映` | 何を直したか不明 |
| `fix: レビュー対応` | 同上 |
| `chore: 修正` | 何の修正か不明 |
| `fix: コメント対応` | 同上 |
| `feat: 実装` | 何を実装したか不明 |
| `fix: 諸々修正` | 複数変更を丸めている |

#### 良い例

```
fix: UserRepositoryがPresentation DTO(AuthUserPayload)を返す依存方向を是正
feat: 推移表AIアドバイスに月カラム選択UIを追加
fix: v-forのkeyをindex→posting_idに変更してDOM再利用の不整合を防止
refactor: テスト命名をtest_<動作>_<条件>_<期待結果>の順序に統一
fix: AccountTitleSerializerにthree_month_averageフィールドが存在しないAttributeErrorを修正
```

#### 変更が複数テーマにまたがる場合は複数コミットに分ける

1つのコミットメッセージで表現しきれない変更は、**テーマごとに分けて複数コミットにする。**

```bash
# ❌ Bad: 1コミットに詰め込む
git add -A
git commit -m "fix: 諸々修正"

# ✅ Good: テーマ別に分割
git add backend/app/features/user/
git commit -m "fix: UserRepositoryのDTO依存方向を是正"

git add frontend/src/features/auth/
git commit -m "fix: ChangePasswordModal.vueのFloating Promiseをvoid修飾に修正"
```

#### 過去のコミットログの参照について

過去のコミットログは**prefixスタイルの参照のみ**に使う。過去のコミットメッセージの品質が高い保証はないため、メッセージの内容・詳細度・書き方を過去に合わせてはならない。常にこのスキルのルールに従って高品質なメッセージを生成する。

#### その他のルール

- **日本語**で記述する（OSSプロジェクトは英語。CLAUDE.mdルール準拠）
- **技術用語の表記**: 公式表記を遵守する（GitHub, RuboCop, TypeScript, Next.js, PostgreSQL, nginx 等）
- **コミット粒度**: 独立してリバートできるアトミックな単位。ステージ済みの変更が複数の論理的変更を含む場合、コミットの分割を提案する

### ステップ6: ユーザー確認（1回のみ）

以下の内容をまとめて1回だけ確認する:

- **ブランチ**: 現在のブランチ名
- **ステージ対象**: ステージするファイル一覧（既にステージ済みの場合はその旨）
- **コミットメッセージ**: 生成したメッセージ全文
- **push**: 実行するかどうか

ユーザーの承認後、以下を順次実行:
1. ファイルのステージ（必要な場合）: `git add` で個別にステージ
2. コミット実行（HEREDOC形式）:

```bash
git commit -m "$(cat <<'EOF'
コミットメッセージ1行目

本文（必要な場合）

Co-Authored-By: Claude Opus 4.6 <noreply@anthropic.com>
EOF
)"
```

3. `git push`（確認済みの場合のみ）

### ステップ7: hook失敗時の対応

pre-commit hookが失敗した場合:

1. エラー内容を分析
2. 問題を修正
3. 修正ファイルを再ステージ
4. **新規コミット**を作成（`--amend` は絶対に使わない。hookが失敗した場合コミットは作成されていないため、`--amend`は前のコミットを書き換えてしまう）

## Strategy Selection

### Strategy B: New Commit（デフォルト）
独立した新しいコミットを作成する。**これがデフォルト。**

### Strategy A: Squash/Amend
直前のコミットへの軽微な追記（誤字修正・コメント追加等、内容が完全に同一テーマ）のみ使用。**明示的に指示された場合のみ。**
```bash
git commit --amend --no-edit
git push --force-with-lease
```

### Strategy C: Interactive Rebase
複数コミットを整理したい場合。**明示的に指示された場合のみ。**
```bash
git rebase -i origin/dev
git push --force-with-lease
```

## 禁止事項

- `--no-verify` は使わない
- `git add -A` は使わない（個別にステージする）
- `.env`、認証情報、シークレットファイルのコミットは警告する
- main/master/devブランチへの直接コミットは絶対NG
