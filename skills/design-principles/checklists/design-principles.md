# Review: Design Principles（SOLID / デメテルの法則 / クリーンコード）

このチェックリストはサブエージェント用。担当スタック（`backend/` または `frontend/`）の変更ファイルに対して **言語非依存** で適用する（Python/TypeScript 共通の設計品質の観点）。フロント・バック両方に変更がある場合は、本チェックリストを読む設計エージェントがスタックごとに2つ起動する。

各観点は「設計の綺麗さ」のレンズ。バグ検出は他チェックリストに任せ、ここでは責務・依存・凝集/結合・複雑性を見る。既存チェックリストと重なる項目は重複指摘せず、設計原則の観点でのみ拾う。

---

## Core Checklist

### SOLID

- [ ] **単一責任（SRP）** — クラス/モジュール/関数が変更理由を1つに保っているか。「〜と〜をする」と and でしか説明できない単位は分割対象。肥大化した God class や雑多なユーティリティの寄せ集めに注意
- [ ] **オープン・クローズド（OCP）** — 種類の追加のたびに既存の `if/elif`・`switch` 分岐を編集していないか。多態・ストラテジ・マップで拡張点を開き、既存コードの改変を避ける（既存の「Enum網羅分岐」ルールの一般化）
- [ ] **リスコフ置換（LSP）** — サブクラス/実装が基底の契約を破っていないか（例外を強める・戻り値の意味を変える・一部メソッドを `NotImplementedError`/`throw` で無効化する等）。is-a が成り立たないなら継承しない
- [ ] **インターフェース分離（ISP）** — 利用側が使わないメソッドまで抱える太い interface/Protocol になっていないか。役割ごとに分割する。実装側に空実装・ダミーが生えていたら兆候
- [ ] **依存性逆転（DIP）** — 上位（方針）が下位（詳細・インフラ）の具象に依存していないか。抽象（Protocol/IF）に依存し具象は注入する（既存の Clean Architecture / FSD 依存方向ルールの一般原則）

### Law of Demeter（最小知識の原則）

- [ ] **train-wreck 呼び出し** — `a.getB().getC().doD()` のように他オブジェクトの内部を辿って深く呼んでいないか。直接の協力者にのみ語りかけ、必要な操作は委譲メソッドとして公開する
- [ ] **内部構造の漏洩** — 呼び出し側が相手の内部データ構造（ネストした dict / 属性チェーン）に依存していないか。Getter チェーンより「相手に仕事を頼む」設計に寄せる

### Coupling & Cohesion

- [ ] **低結合** — モジュール間が具象・グローバル状態・暗黙の実行順序で密結合になっていないか。境界はインターフェース/イベント/引数で疎に保つ
- [ ] **高凝集** — 関連する責務とデータが1か所にまとまっているか。あるデータを別モジュールが頻繁に取り出して操作する（feature envy）状態になっていないか

### Clean Code（一般原則）

- [ ] **Tell, Don't Ask** — 相手の状態を取り出して呼び出し側で判断するのではなく、判断ごと相手に委譲しているか
- [ ] **YAGNI / 過剰な抽象化** — 今必要ない汎用化・設定可能化・フック・将来用パラメータを先回りで作っていないか。使われない拡張点は削る
- [ ] **KISS / 不要な複雑性** — 同じ結果をより単純に書けないか。深いネスト・過剰なメタプログラミング・賢すぎる一行を避け、早期 return 等で平坦化する
- [ ] **コマンド・クエリ分離（CQS）** — 値を返すクエリが副作用を持っていないか（取得のついでに更新する等）。状態変更（コマンド）と取得（クエリ）を分ける
- [ ] **単一抽象レベル（SLAP）** — 1つの関数内で高レベルの手順と低レベルの詳細が混在していないか。詳細は名前付きヘルパーに抽出する
- [ ] **継承より合成** — 振る舞いの再利用目的で継承していないか。is-a でない再利用は合成/委譲で行う

## Extended Checklist

- **Rule of Three（抽象化の早すぎ/遅すぎ）** — 重複は2回までは許容し、3回目で共通化する。1例だけで抽象を作らない（逆に3箇所の重複放置もNG）
- **副作用の局所化** — I/O・グローバル状態変更・時刻/乱数等の副作用が、深い純粋ロジックに紛れていないか。副作用は境界に押し出す
- **ブール引数 / 制御フラグ** — `doX(true)` のような意味の読めないフラグ引数で1関数が2つの責務に分岐していないか。関数を分けるか enum/オプションオブジェクトにする
- **プリミティブ執着** — 意味のある概念（金額・ID・期間・コード等）を生の str/int で持ち回っていないか。値オブジェクト/branded 型で表現する（既存の Amount 型ルールの一般化）
- **過度なモックは結合の兆候** — テストで多段（`a.b.c` を mock）やモック数が多すぎる場合、対象の結合が深い設計上のサインとして指摘する
- **命名と責務の一致** — 名前（`*Manager`/`*Helper`/`*Util` 等の曖昧語、または実態と乖離した名前）が責務の不明瞭さ・SRP違反を示していないか
